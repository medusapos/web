## Setup problems

- **CORS errors:** check that both `ADMIN_CORS` and `AUTH_CORS` include the exact origin you opened, including HTTPS and any port. Restart the backend after changing them.
- **Sign-in says "Could not reach the backend":** check the backend URL and that the backend is running. With a `localhost` backend, Chrome also needs the POS's permission to access your local network: allow it from the prompt, or from the site settings (the icon left of the address bar).
- **"Missing shipping option":** configure a shipping option at the POS stock location, or set `shippingOptionId` in the plugin options and restart.
- **Sign-in says "not supported yet":** multi-factor sign-in is not supported; use an admin account with email/password sign-in and no MFA.

## Check sync status

While a sale hasn't reached the store, **Products** shows how many sales are waiting to sync. **Orders** lists each as **Waiting to sync**. When all have synced, it says "Sales are up to date."

## Read the banners

### Sign in again

Your sign-in expired. A strip says your sales are saved and waiting to send, with a **Sign in** link. Enter your password there to send them.

### Not accepted

The store refuses a whole batch. The strip says "N sales not accepted · Details". Use **Try again** once the store is fixed. Those sales stay safely on the till.

A batch refused for its size, more than 50 sales or over the size limit, is different: there is nothing in the store to fix, and the till can't split it yet. The sales stay on the till; splitting comes in a later version ([Till limits](/docs/limitations#till-limits)).

### Saved sales can't be opened

The full-screen message says "Saved sales can't be opened on this device. Nothing has been deleted. Reload to try again, or report the problem." It offers **Reload** and **Report a problem**, sometimes with an error code underneath.

## "This account can't use the POS"

The store has Medusa RBAC on, and this user has neither POS role. A store owner gives them the **POS cashier** or **POS manager** role in Medusa Admin, as in the quick start's [Choose who may use the POS](/docs/quick-start#choose-who-may-use-the-pos).

## Review orders that need attention

Open **Orders** → **Needs attention**. A sale the store rejected shows **Retry**, which sends it again. Some rejections instead say the sale needs checking against the store first; those have no **Retry**.

### Held sales

A sale with no **Retry** is held because its order was changed by hand in Medusa, for example refunded, partly captured, paid with another payment provider, or with a cancelled fulfilment. The store logs one line for it:

```text
tally order.create needs admin: command <commandId>, order <orderId>: <detail>
```

Whoever runs the Medusa backend clears it from the store's backend directory, using the command id from that line:

```sh
npx medusa exec node_modules/@medusapos/medusa-plugin/.medusa/server/src/scripts/tally-ledger-resolve.js <commandId> apply
```

If your backend is in an npm or Yarn workspace, the plugin is usually installed in the workspace root's `node_modules`, not the backend's. If that path doesn't exist, point the command at the plugin's copy there, for example `../../node_modules/@medusapos/medusa-plugin/…`.

- `apply`: you have fixed the order by hand. The till's next resend finishes the sale.
- `reject` (in place of `apply`): takes back any stock the plugin added for the sale and cancels its order. The till's next resend gets a rejection. If the order can't be cancelled, the sale stays held: cancel it by hand in Medusa Admin and run `reject` again, not `apply`.

A warning can accompany a successfully synced sale, for example when stock is short. A rejected order needs investigation.

## Sell offline

You can keep selling from the catalogue already loaded on the device. Each sale queues and is sent to Medusa when you're back online, and Medusa never records it twice. The first sign-in and initial catalogue load need a connection.

After that, store settings are cached, so a till that is already open keeps working while it can't reach the store, with an **Offline** note and **Retry**. There is no offline page cache, so reloading or reopening the app while offline fails. A reload while online keeps sales still waiting to sync.

## Keep one live tab per store

Opening a second tab makes it take over. The first shows "MedusaPOS is open in another tab" with **Use here** to take it back. Closing the live tab lets a waiting tab take over.

A browser without the private storage MedusaPOS needs shows "MedusaPOS can't run in this browser".

## If a sale can't be saved

The payment screen stays on the sale. **Complete sale** tries again; pressing it again never saves the sale twice.

Once the sale is saved on the till, **Continue** starts the next sale and the saved one is sent as usual. **Sign out** stays greyed out until the sale is saved or you continue. If **Continue** never appears, write the sale down, reload the app and report it.

## Storage messages

- **Storage stopped … Reload**: the device's local storage worker died. This is rare. Reload the tab; sales already saved are kept.
- **Saving is slow…**: a transient note. No action is needed.

## Check catalogue freshness

- Stock is checked against the store every 5 minutes and when the app returns to the foreground. Each variant's stock label says when it was last checked.
- Prices are re-checked every 30 minutes, and base prices nightly.
- Deleted products and variants are removed at app start and every 24 hours while the app stays open.

Signing out clears the local catalogue. Sign in again online to load it fresh.

## Updating to 0.2.0

These instructions apply when you update from 0.1.0 to 0.2.0, which changes how each till stores its sales. Update the plugin first (see [Update the plugin](/docs/changelog#update-the-plugin)), then the tills. The hosted app at `https://app.medusapos.com` updates itself: reload each till's tab once its sales have synced.

Before updating, make sure every till has sent all its sales, with nothing waiting to sync. Sales saved before the update carry over when the till upgrades its storage.

After updating, don't install an older version again. It can't read the new storage, shows none of the till's sales and doesn't send those still waiting. If a till shows no sales after going back to an older version, don't ring those sales again: update the till and they come back.

## Report a problem

**Send feedback** on the sign-in or **Orders** screen opens a GitHub issue form. You can also [open the feedback form](https://github.com/medusapos/app/issues/new?template=tester-feedback.yml).

It asks for app version, backend host, device and browser, what happened, steps and what you expected. The backend URL is always reduced to its host.
